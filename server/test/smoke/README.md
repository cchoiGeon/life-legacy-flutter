# 스모크 — 실제로 뜬 서버를 HTTP로 훑는다

단위 spec(`npm test`)은 서비스 규칙을, e2e spec(`npm run test:e2e`)은 부팅 배선을 본다.
여기 있는 둘은 **진짜 서버에 요청을 쏴서** 그 사이에 있는 것들 — 상태코드, 응답 모양,
DB에 실제로 남은 값, 트랜잭션 경계 — 을 확인한다.

## 쓰는 법

```bash
# 1. 서버를 띄운다
npm run start:local

# 2. DB를 비운다 (사용자 데이터만. 시드는 남는다)
psql -d lifelegacy_app -c "truncate app_user cascade"

# 3. 돌린다
bash test/smoke/atoz.sh
```

> ⚠️ **사용자 표를 지운다.** 개발용 로컬 DB에서만 돌릴 것.

## atoz.sh — 22단계 117개 검사

가입부터 자서전까지 한 사용자의 전 생애를 따라간다.

| 단계 | 보는 것 |
|---|---|
| 0–4 | 헬스체크·프리픽스, 인증번호 발급·재발송 억제, 검증 실패 3갈래, 인가 |
| 5–8 | 자기소개 순서 강제, 케이스 판정(10장↔9장), 재제출 시 옛 목차 폐기, 목차 재배열 확정 |
| 9–11 | 홈·현재 질문 일치, 소유·잠금 검사, 질문 문구 수정 |
| 12–14 | 1차 답변→꼬리질문(초안만), 확정 저장, 건너뛰기, 장 완주→다음 장 잠금 해제 |
| 15–18 | 자서전 쪽 나누기, 홈 진행률, 알림 읽음, 설정·배송지 |
| 19–22 | 토큰 회전·재사용 차단, 로그아웃, 재로그인 시 `needs_intro=false`, 사용자 격리 |

응답만 보지 않고 **DB를 직접 조회해서** 확인하는 것들:
초안이 확정 전엔 1건·후엔 0건, `keyboard`면 `spoken_seconds`가 NULL,
저장된 원문이 마지막 1차 답변과 일치, 장 상태가 `done/writing/locked`로 옮겨졌는지.

## ai-failure.sh — AI 실패 두 갈래

`AiService`는 `AI_PROVIDER`가 `stub`이 아니면 던진다. 그 성질을 이용해
**실제 AI 제공자 없이** 실패 처리를 검증한다. 스크립트가 서버를 알아서 재기동한다.

| 갈래 | 기대 |
|---|---|
| 윤문 실패 | `422 POLISH_FAILED` · 초안 **남음** · 확정 저장 안 됨 |
| 꼬리질문 생성 실패 | `422 FOLLOWUP_FAILED` · 그 질문 초안 **삭제** · 다른 질문 초안은 무사 |
| AI 복구 후 재전송 | `200` · 1차 답변이 유실 없이 그대로 저장 |

## 안 보는 것

- **실제 AI 제공자** — 붙은 뒤에 응답 품질을 따로 봐야 한다
- **카카오 로그인** — SDK가 아직 없다
- **부하·동시성** — 같은 질문에 두 요청이 동시에 들어오는 경우
